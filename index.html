01 / FOUNDATION

What is a Binary Search Tree?

ONE plain sentence: a BST is a way of storing sorted data so you can find any item by repeatedly cutting the search space in half — like guessing a number when the only answer you get is "higher" or "lower".

Start with that number game. I pick a number between 1 and 100. Your smartest move is to guess 50. I say "higher". Now you know it's 51–100, so you guess 75. Two guesses have already eliminated 75 numbers. A BST makes your computer play exactly this game against its own data.

It's a treeA structure with one top node (root) where every node points to nodes below it (children). Family tree, org chart, folder structure — all trees.: one node at the top called the root, and each node holds a value plus (at most) two links — left and right. That's the "binary" part: two children max.

THE ONE RULE

Everything in the left subtree < the node < everything in the right subtree.

Not just immediate children — the ENTIRE left side, all the way down. This single rule is the whole data structure. Everything else follows from it.

WHAT A NODE LOOKS LIKE
{ value: 50,
  left:  → node or null,
  right: → node or null }

That's it. A number and two arrows. A BST with a million nodes is just this shape repeated a million times.

THE PAYOFF

Because of the rule, every comparison throws away half the remaining tree. Search, insert and delete all follow one root-to-leaf path, so they cost height, not size.

1,000,000 items → about 20 steps (if balanced). An unsorted array would need up to 1,000,000.

WATCH OUT

A BST is defined by the ordering rule, not by how it's drawn. The same 7 values can be arranged into many different BSTs — including a miserable straight line (see the Balance section). Good arrangement = fast; bad arrangement = slow.

02 / THE CONTRACT

The BST rule, precisely

For EVERY node: all values in its left subtree are smaller, all values in its right subtree are larger — checked all the way down, not just one level.

People get this wrong constantly, so let's be exact. It is NOT "left child < node < right child" (that's only one level). The correct statement involves entire subtreesA node plus all of its descendants — a mini-tree hanging off a bigger one. Every node is the root of its own subtree.:

For every node X with value v:
  every value in X.left's subtree  < v
  every value in X.right's subtree > v

✔ Valid BST

Check 50: left side {30,20,40} all < 50, right side {70,60,80} all > 50. Check 30: {20} < 30, {40} > 30. Every node passes.

✘ NOT a BST

Looks innocent. But 55 sits in the LEFT subtree of 70, which sits in the RIGHT subtree of 50 — so 55 must be > 50. It isn't. Rule broken, BST is dead.

DUPLICATES

Classic BSTs (and this whole site) assume all values are distinct. If you must store duplicates, the usual convention is "equal goes right" (or keep a count in the node) — but then be consistent everywhere. Interviewers love asking about this.

03 / INTUITION

Why is it fast? (Big-O, in plain English)

Each comparison kills half the remaining candidates, so ~1,000,000 items need only ~20 comparisons. That log₂ n is the entire superpower of a BST.

Big-O"How does the work grow as the data grows?" O(n) = work grows with the data; O(log n) = work grows with the number of times you can halve the data. Big-O ignores constants, keeps the growth shape. notation describes how the work grows. The key player here is O(log n)log₂ n = how many times you can cut n in half before reaching 1. n=1,000,000 → 20 cuts. Doubling the data adds ONE step. — "log n" is literally "the number of times you can halve n". That's the number-guessing game again:

THE CATCH

log n is only true for a bushy tree. Insert 10, 20, 30, 40, 50 (already-sorted data — extremely common) and every node goes right: you get a staircase, height = n − 1, and search is back to O(n). This is exactly why self-balancing trees exist — Balance section.

06 / WALKTHROUGHS

Traversals — visiting every node

In-order walks a BST in SORTED order (this is the party trick). Pre/post-order are for copying, deleting and evaluating trees. Level-order reads it top-down like a fan wave.
Visit order:
IN-ORDER — sorted output

Recursively: left subtree, then the node, then right subtree. On ANY valid BST this prints values in ascending order. It's how you dump a BST to a sorted list, validate it, or debug it.

PRE-ORDER — copy a tree

Node first, then children. The output lets you rebuild the exact same tree (insert in that order) — used for serializing BSTs.

POST-ORDER — delete a tree

Children first, node last. You can't delete a node before its children are gone, so post-order is the natural "free the whole tree" order. Also how expression trees get evaluated.

LEVEL-ORDER — by rows

Uses a queueFirst-in-first-out list. Add children to the back, take nodes from the front — the rows come out in order. instead of recursion. Used for printing the tree by depth, and in the "is it balanced?" check.

07 / IMPLEMENTATION

Deletion — the only tricky operation

Deleting a node has 3 cases: a leaf (just remove it), one child (child takes its place), two children (replace its value with its in-order successor, then delete that successor deeper down).

Search and insert are one clean walk down; you've watched them in the Playground. Deletion is where implementations get tangled, so here is the full logic, exhaustively commented:



  

    
CASE 1 — LEAF
Node has no children (like 20 or 80 in the demo tree). Just cut it off. Nothing else moves.

    
CASE 2 — ONE CHILD
Node has exactly one child. Splice: the child takes the node's place. (Also covers the "node has only a right child" variant.)

    
CASE 3 — TWO CHILDREN
The node's value is replaced by its in-order successor — the smallest value in its right subtree (leftmost node down the right side). Then delete that successor (it has at most one child, so it falls back to Case 1 or 2).

  


  

    
WHY THE SUCCESSOR WORKS

    
The in-order successor is the smallest value that is still bigger than the deleted node — it's the only candidate that keeps every order relationship intact: bigger than the whole left subtree, smaller than the rest of the right subtree.

  







  
08 / THE ACHILLES HEEL

  
Balance — the BST's weak spot

  
Insert sorted data and your "fast" BST silently degrades into a linked list. Self-balancing trees (AVL, Red-Black) rotate nodes on every insert so the height stays ~log n forever.


  

    

      
BUSHY — height 3

      
      
Values 10–70 inserted as 40,20,60,10,30,50,70. 7 nodes, height 3, any search ≤ 3 steps. This is what log n feels like.

    

    

      
STAIRCASE — height 7

      
      
The SAME 7 values inserted sorted (10,20,30,40,50,60,70). Height 7, finding 70 takes 7 steps. Same rule satisfied — terrible shape. Insertion order decides everything.

    

  


  
What balanced trees do about it

  

    

      
AVL TREE

      
Every node stores its height; after each insert/delete the tree checks each ancestor's balance factor (left height − right height). If it hits ±2, a rotation rearranges 2–3 nodes locally and the height shrinks back. Strictest balance → fastest lookups, more rotations on writes.

    

    

      
RED-BLACK TREE

      
Nodes are coloured red/black under 5 rules that keep the longest path ≤ 2× the shortest. Looser than AVL → fewer rotations, slightly taller trees. This is what C++ std::map, Java TreeMap and Linux's CPU scheduler use.

    

    

      
THE ROTATION, IN ONE BREATH

      
A rotation promotes one child to parent and demotes the old parent to its child, keeping the BST RULE intact — 3 pointers change. It's the single move that fixes every imbalance.

    

  

  

    
IF YOU JUST NEED A SORTED DICT

    
You almost never hand-roll a balanced BST — use the language's built-in one (C++ std::map, Java TreeMap) or a sortedcontainers.SortedDict in Python. Hand-rolling is for learning and interviews, which is exactly what this page is for.

  







  
09 / CONTEXT

  
BST vs everything else

  
Use a BST when you need sorted-order operations (floor, ceiling, ranges, "next bigger") on changing data. Use a hash table for pure get/put speed. Use an array when data never changes.

REAL-WORLD USERS

    
Database indexes (B-trees — the on-disk sibling of a BST), C++ std::map/std::set, Java TreeMap/TreeSet, event schedulers ("what fires next?"), autocomplete prefix structures, and the Linux kernel's CFS scheduler all live on this family of trees.
